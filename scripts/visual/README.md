# 视觉回归（截图对比）

## 为什么需要它

本项目原有 2263 项断言，**全部是行为级或静态守卫——没有一项能证明「画面看起来是对的」**。

历史上真实发生过的几何缺陷，都是靠人工算坐标才发现、并反复修不干净的：

| 问题 | 发现方式 |
|---|---|
| 顶排筹码被底池遮挡（2026-10-19 用户反馈） | 用户报障 |
| uh / felt% 单位混算（元凶，修了三天） | 人工推导坐标 |
| 8 位桌 `EIGHT` 模板缺 1 项 → 兜底座贴死 | review 时写脚本算坐标 |
| 补项后内侧位 x=10 与外侧交叠 | 同上，第二轮才算出来 |

**算坐标只能证明「数学上不重叠」，证明不了观感好不好**；而且算错坐标会得出完全相反的结论——本项目 review 过程中真实发生过三次（用了错误的块宽、错误的单位基准、只查纵向不查横向）。

截图对比把「布局对不对」变成一眼能确认的事。

## 怎么用

```bash
npm run visual          # 渲染全部场景 + 与基线比对（CI 式，有差异则退出码 1）
npm run visual:render   # 只渲染到 scripts/visual/out/
npm run visual:update   # 确认画面变化符合预期后，用当前结果覆盖基线
```

单独跑某个场景：

```bash
node scripts/visual/run.js --only ai-8p
node scripts/visual/compare.js --report   # 只打印差异统计，不判失败
```

输出在 `scripts/visual/out/`：每张图同时产出 `.png` 与 `.html`，**HTML 可以直接用浏览器打开**，比 PNG 更好排查（能开 devtools 看盒模型）。

## 工作原理

```
真实页面 JS ──(mock wx/Page + 假时钟)──→ 真实 data 快照
                                              │
真实 table.wxml ──(WXML 渲染器)──→ HTML 片段 ──┤
                                              ├──→ 完整 HTML ──(Chrome headless)──→ PNG
真实 table.wxss ──(单位换算)────→ CSS ────────┘
```

关键点：**不另写演示页面，复用页面自己的 data**。仓库里的 `index.html` 是自绘样式（没有 `--uh`、没有 `.felt`），和小程序是两套东西，拿它做回归测不到真实画面。

- `wxml-render.js` — WXML → HTML：支持 `wx:if/elif/else`、`wx:for`、`{{ }}` 插值（文本与属性位置）
- `wxss-render.js` — WXSS → CSS：`rpx` 按**宽度**/750 换算，`var(--uh)` 按 `min(w,h)/100`，`var(--uw)` 按 `w/100`。三者基准不同，不能合并
- `runtime.js` — mock 小程序运行时 + 假时钟（同步推进 setTimeout，让异步开局瞬间完成）
- `scenes.js` — 场景定义：2/5/6/7/8/9 人桌 × 3 视口
- `compare.js` — 手写 PNG 解码（zlib 反滤波），逐像素比对 + 连通块分析
- `selftest.js` — 工具自检 29 项，**已并入 `npm test`**（纯 JS，不依赖浏览器）

## 两个决定成败的坑

### ① 渲染必须确定，否则基线永远不稳

页面开局用 `seed: 'mp-' + Date.now()` 做牌种。第一次实现时没接管 `Date.now`，结果**18 张图有 14 张每次运行都不一样**，基线比对完全没法用。

解决：假时钟用**固定 epoch**（`1735689600000`）而非真实时间，同时固定 `Math.random`。修正后 15/18 张字节级一致，剩余 3 张是 Chrome 抗锯齿抖动（差异 < 0.04%）。

### ② 场景参数必须真的生效

`maxSeats` 由 `opts.max` 决定（默认 6），`bots` 只决定补几个 bot。只传 `bots` 不传 `max`，所有桌型都会被截到 6 座、渲染出同一张图——这个 bug 是靠比对文件 hash 才发现的（6 张 PNG 字节数完全相同）。

## 判定阈值

```
像素差总和 > 24 才算「变了」（滤掉编码抖动）
变化像素 > 0.5%  且  最大连通块 > 0.15%   → 判失败
```

为什么看连通块而不只看比例：抗锯齿、字体渲染差异是**零散细线**（连通块极小），而真实布局问题（座位挪位、元素被裁、遮挡）一定是**连成大片**的区域。

实测校准（注入 8 位桌 x=10 交叠 bug）：

| 场景 | diff | blob | 判定 |
|---|---|---|---|
| ai-8p × 3 视口 | 3.1~3.2% | 0.45~0.46% | ✗ 正确拦截 |
| ai-2p × 3 视口 | 0.006~0.040% | 极小 | ~ 抖动，未误报 |
| 其余 9 张 | 0 | 0 | 完全一致 |

**零误报，精准命中。**

## 维护约定

- 改了**布局相关**（座位坐标、屏幕上的元素尺寸/位置）→ 跑 `npm run visual`，肉眼确认 `out/*.png` 符合预期后再 `npm run visual:update`
- 改了**纯逻辑**（同步、结算、AI 策略）→ 理论上画面不变，`npm run visual` 应直接通过；若报红，说明改动意外影响了渲染，值得查
- 基线图（`baseline/*.png`）18 张约 3.5MB，**要进版本库**——否则别的机器第一次跑没有基线可比
- 新增场景：在 `scenes.js` 里加一条，跑 `npm run visual:update`

## 环境要求

需要本机有 Chrome 或 Edge（脚本会自动找常见安装路径，也可用 `CHROME_PATH` 环境变量指定）。

找不到浏览器时脚本**不会失败**，只产出 HTML 并提示——保证在无浏览器的 CI 上不阻断流程。真正的比对仍需要基线图。
