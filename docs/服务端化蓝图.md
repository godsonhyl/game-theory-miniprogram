# 房卡 / 战绩 / 签到服务端化蓝图

> 2026-10-15 · 来源：全项目评审 MEDIUM「商业化硬前提」（战绩纯客户端自报可刷 →
> 对局奖励无限领；签到三段非原子可双领）。本文档是**启用房卡货币化之前必须完成
> 的服务端改造清单**——当前客户端态只是演示，任何一处不改都不能接支付。
> 评审当天在客户端层做了两处收口（见文末「已落地的客户端收口」），消掉了最
> 浅的两类并发漏洞；其余全部需要服务端代码，客户端无解。

## 现状与风险账本

| # | 缺陷 | 攻击面 | 客户端能否自修 |
|---|------|--------|----------------|
| 1 | `total_hands` 由客户端每手上报 +1（auth.js `saveRecord`） | 抓包/反编译后直接 insert 流水或 update 档案，手数任意拉满 → 每逢 10 手白拿房卡 | ❌ 必须服务端生成战绩 |
| 2 | 签到三段非原子（读档案 → 发卡 → 置 last_checkin，标记失败被吞） | 断网重放/双端并发：同一天重复发卡 | ⚠️ 已部分收口（标记先行 + 乐观锁），残余窗口见下 |
| 3 | 签到日期用**客户端**日期（auth.js `today()`） | 改设备时间无限领 | ❌ 服务端时钟 |
| 4 | 房卡扣减靠房间余额乐观锁 | 并发轮询重试可绕 | 已有 CAS，事务化后更强 |
| 5 | 领取无发放流水 | 任何异常无法审计/追账 | ❌ 服务端流水表 |

## 目标架构

所有写入口收进数据库层：**「算钱」的请求必须经过一个服务端函数，客户端只剩
调用权**。WorkBuddy 云提供 PostgREST 直连表 + `rpc()` 调用 PostgreSQL 函数的
能力（SDK `database.rpc(fn, args)`，miniprogram.js:9500+）——四套函数建议
全部用 SECURITY DEFINER 的 PL/pgSQL 实现并 revoke 客户端对表的直接 update。

### 建表/改表

- `poker_profiles`：把 `room_cards`、`total_hands`、`bonus_base`、`last_checkin`
  的 column 权限收成「服务端函数可写、客户端只读」；客户端保留 update 的字段
  白名单只剩 `nickname`/`avatar`（或干脆全部走函数）。
- 新表 **`poker_card_grants`**（发放流水）：
  ```sql
  CREATE TABLE poker_card_grants (
    id          bigserial PRIMARY KEY,
    owner_id    uuid NOT NULL DEFAULT auth.uid(),   -- 同 profiles：客户端不传
    kind        text NOT NULL,          -- 'daily' | 'hands' | 'refund' | 'purchase'
    amount      int  NOT NULL,
    balance_after int NOT NULL,         -- 出账即审计，事后对账不再翻全表
    day         date,                   -- kind='daily' 时记，幂等键的一半
    hand_base   int,                    -- kind='hands' 时记推进后的 bonus_base
    created_at  timestamptz NOT NULL DEFAULT now()
  );
  ```
- `poker_records`：不收权限（它是事实流水，务必完整，客户端能不能写不影响
  防刷）——只把你的 `poker_profiles.total_hands` 不再交给这条链路加总。

### 服务端函数（rpc）

1. `poker_claim_daily(p_day date)` —— 签到：
   - 幂等键 `(auth.uid(), p_day)`：**先插流水（唯一约束卡的幂等）那张**
     `poker_card_grants(kind='daily', day=p_day)`，直接终止 = 已领；
   - 只有插入成功的那一行才同事务 `UPDATE poker_profiles SET room_cards =
     room_cards + N, last_checkin = p_day`；返回新余额；
   - `p_day` 参数只在**服务端**接受；是否参用 `current_date` 由函数内部
     说了算（不要相信客户端任何计算）。
2. `poker_claim_hands()` —— 对局奖励：同模式，以
   `total_hands - bonus_base` 段拉档（保留单次 5 张上限），一条语句完成并发
   抢占；分母不再依赖补转行（录入战绩函数重回事务, update counter）。
3. `poker_consume_room_card(p_count int)` —— 建房扣卡：余额校验 + 扣减 +
   流水在同一个事务（无限重试窗口彻底消掉「不足额扣去」半步差）。幂等凭据
   （创建房间前先生成的 `room_no` 或一次性 token）由客户端随请求传入。
4. `poker_record_hand(p_row jsonb)` —— 战绩上报：插入 `poker_records` 并在
   同一函数里 UPDATE 档案累计（表权限收掉后，客户端不再能直接 update
   `poker_profiles`，刷手数从根上死掉）。如果将来战绩要成为「战绩页」数据源，
   也顺手在服务端用快照聚合（物化视图）替代 `total_hands` 全表扫描。

### 客户端对应改造

- `auth.js` 的 `claimDailyCards/claimHandBonus/consumeRoomCard/saveRecord` 全部
  换成 `cloud.database.rpc('poker_claim_daily', { p_day: ... })` 一类的调用，
  拿返回值照旧走 UI；
- `today()` 删除——日期参数从 `poker_claim_daily` 的返回值里读；
- 失败分支不再有「三段提交」中间态，UI 提示跟函数的 raise 文案走。

## 残余窗口声明（改造前的过渡期风险）

- 签到与对局奖励都改成了**「置资格标记 → 发卡」**两段：并发双击里只有抢到
  标记的一方走发卡，进入方向不发多；但「标记成功、发卡失败」的窗口仍是
  非原子的——用户当天可能被误判已领（少发，非多发）。方向上选择宁可少发：
  线上出现多发要服务端追账，少发只是次日自愈的体验瑕疵。服务端函数落地后
  窗口归零。
- `total_hands` 仍是客户端自报：**在函数 4 上线前，房卡不得接任何真实支付**，
  现有 free 卡发放也要接受「奖励手数被刷」作为演示期的已知风险。

## 已落地的客户端收口（2026-10-15，随本文档同提交）

- `claimDailyCards`：last_checkin 先行置位（读到的旧值做乐观锁条件——NULL 旧值
  走 `is(column, null)`，PostgREST 的 `eq` 对 NULL 永不命中，这个坑会让历史
  空值行永远领不了卡）再发卡，同日双端并发不再能双领；残余窗口 = 标记成功后
  发卡失败（少发）。
- `claimHandBonus`：bonus_base 乐观锁推进 + 冲突重读重试，基准推进与发卡张数
  绑定，重复领取不再多发。
- `saveRecord`：累计统计（total_hands 等）UPDATE 加 `.eq('total_hands', 读值)`
  乐观锁 + 0 行重试，连打两手不再互相覆盖少计。
- 以上均有 test-cards.js 行为断言（并发改库后旧调用失败、重读后成功、NULL
  历史行可领等，40 → 55 项）。
